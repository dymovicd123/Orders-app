## Не загрязнять GitHub

1. **Не создавать `oneoff-*.yml`, workflow под отдельный PR/дату/SHA, временные ветки и скрипты без реальной необходимости.** Использовать существующие `quality-check.yml` и тематические тесты. Новый повторно используемый workflow допустим лишь когда имеющихся принципиально недостаточно, с объяснением.
2. **Не копировать целиком `App.tsx`, `worker/index.ts`, большие runtime-файлы в `scripts/fixtures/`.** Для тестов использовать минимальный вход, маленькую фикстуру и реальные HTTP/SQLite сценарии.
3. Старые тесты сначала классифицировать: активный критический контракт, change-scoped, историческая фикстура, дубликат или мусор. Проверить ссылки и сценарии перед удалением. Не подменять поведенческие проверки хрупким `source.includes('огромный буквальный кусок')`.
4. Не отключать красный тест ради зелёного CI. Определи, что сломано: поведение, устаревшее ожидание или runner; документируй причину и проверь реальный инвариант.
5. Сохранять рабочие инструкции **в этих документах**, а не в новых сотнях continuation-файлов. После каждого существенного PR обновлять раздел прогресса в архитектурном аудите.

## Рефакторинг без риска для клиентов

- Один вертикальный срез за PR; сначала отделение/перенос **без изменения поведения**, отдельно — новые правила бизнеса.
- Главные монолиты: `src/App.tsx` (~9 248 строк), `worker/domains/returns-exchanges.ts` (~4 833), `worker/domains/order-reservations.ts` (~3 003), `worker/index.ts` (~2 534), `InventorySection.tsx` (~2 794).
- Очередность: (1) выделить маршруты selective shipping из `worker/index.ts`; (2) разделить returns/exchanges/finance; (3) выделить frontend orchestration из App; (4) постепенно заменить `any` и `@ts-nocheck`. Опирайся на измеренное влияние и полный реальный сценарий.
- **Не удалять старые пути отправки/выдачи без проверки исторических заказов.** Существуют раздельные факты о physical issue, shipment ledger, отменах, обменах и ревизиях.
- Для отправки проверить: all-ready selected by default; partial quantity, включая `unresolved`; no double stock decrement; чужие резервы не менять; повтор requestId идемпотентен; correction не создаёт физический остаток; старые заказы и обмены.
- Для денег: возврат 0 ₸ не создаёт платёж; транзакции не дублируются при повторе; учёт возврата товара отделён от возврата денег.
- Не трогать Arrival и остальные стабильные области без чёткой связи с задачей.

## Изоляция и выпуск

- Начинать с актуальной ветки; изменять через узкий PR, не писать напрямую в `main`.
- `npm run release:check`, `npm run build`, подходящие настоящие Worker HTTP + SQLite тесты, затем Branch2 для изменений бизнес-поведения. Следить **за всеми релевантными красными** CI, а не только Quality check.
- Main — реальные клиенты и данные. **Никаких Production D1-миграций, очисток, backfill и тестовых заказов без отдельного разрешения.** Проверять конкретный Worker/D1 binding и SHA деплоя. GitHub merge и Cloudflare deploy — разные события.
- Любые замеченные архитектурные долги возвращать в `docs/architecture/orders-app-audit-2026-11-08.md`, обновлять статус. Не накапливать их очередными аварийными костылями.
