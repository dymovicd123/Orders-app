## 1. Бизнес-модель и решения

### Бренды — первичное разделение
- **TAUWACH**, **WACHIZEN** — два бренда/две линии продаж.
- Название модели часов — **отдельно от бренда**; одно название может существовать
  в обоих брендах. Уникальность каталога должна включать `brand_id`,
  не путать с уникальностью legacy `catalog_products.name`.
- У каждого бренда отдельные менеджеры, заказы, продажи, долги, платежи,
  возвраты/обмены, касса, отчёты, планы/показатели и видимый набор товаров.
- Администратор может переключать бренд или видеть агрегат с явным
  обозначением, что он общий; менеджер только **свой** бренд.
  Логист и сотрудник приёмки/склада по роли могут работать с обоими
  брендами, всегда видя, к какому бренду относится заказ/вещь.
- **Нельзя** реализовать разделение только JS-фильтром:
  сервер проверяет brand-access для list/detail/mutation/report/export,
  отгрузки, возвратов/обменов, SKU и финансов.
- Для кассового журнала: каждая самостоятельная кассовая запись
  обязана иметь `brand_id`; связанная с заказом наследует его бренд
  и не может быть записана во второй. Транзакции, возвраты и отчёты
  фильтруются на уровне SQL / авторизации. Отдельные независимые
  начальные остатки кассы по брендам.

### Офис и витрина
- Учитываются **ровно два физических источника**: `Офис`, `Витрина`;
  внешнее поступление со склада вне учёта оформляется как обычный
  `Приход` в офис/витрину. Третьего управляемого источника «склад» НЕТ.
- Старые canonical source keys допустимо сохранить только **внутри
  Client3**: `warehouse → Офис`, `boutique → Витрина`.
  Это позволяет повторно использовать проверенные транзакции
  Main с `inventory_stock`, `inventory_reservations`, move/writeoff/
  stocktake/dispatch. Во всём UI и в печатных документах — новые названия.
- На обоих источниках остатки/резервы видны отдельно для каждого бренда
  и конкретного SKU. Совпадающее название модели разных брендов не объединяется.
- Перемещение Офис ↔ Витрина не является продажей/приходом.
  «Готово» у логиста не создаёт физического остатка и не списывает его.

### Характеристики SKU (строгая идентичность)
- Наименование модели; бренд; пол **Мужской/Женский**.
- Механизм **Кварц/Механика**.
- Материал браслета **Стальной/Кожа/Каучук**.
- **Цвет циферблата**: Чёрный, Белый, Серебро, Золотистый, Зелёный,
  Оранжевый, Коричневый, Комбинированный.
- **Цвет браслета**: отдельное поле; на первом этапе требуется
  только при материале **Кожа**. Для других материалов отсутствует
  в variant identity, если позднее клиент не расширит требования.
  Кожаный чёрный и кожаный коричневый — **два разных SKU**,
  в приходе/остатке/возврате/обмене их нельзя объединить.
- Поля «Размер» и «Длина» не показывать/не требовать, но
  **не переназначать их тихо** под механизм и цвет браслета
  в SQL. Watch SKU must have explicit dimension storage and
  its own canonical matching; старый resolver clothing-атрибутов
  запрещён как источник догадок.
- `catalog_price` и фактический `sale_price` независимы
  как в Main; с исторической продажей сохраняется snapshot.

### Заказ, отправка и гравировка
1. Менеджер выбирает бренд (если роль уже закреплена — он выбран и заблокирован).
2. Выбирает источник Офис/Витрина, видит свободный остаток своего бренда;
   выбирает модель и точный SKU; оформление без свободного остатка не
   создаёт вымышленный приход, а честно показывает проблему резерва.
3. В строке часов — **«Текст гравировки / комментарий логисту»**.
   Это данные конкретной единицы/позиции, а не один комментарий ко всему
   заказу. Если в одной строке несколько часов с разными надписями,
   необходимо разнести на отдельные позиции/единицы.
4. `Срочный` и дата+время отправки (пример: `15.10, до 17:00`).
   Хранить timestamp с явным бизнес-поясом `Asia/Almaty`;
   не обрезать время до даты. При срочности дедлайн обязателен.
5. «Цех» целиком заменяется **«Логистикой»**, не адаптацией
   расчётов/задолженности производственного цеха.
   Логист видит оба бренда: товар и точный SKU, гравировку,
   срочность/дедлайн, **ФИО получателя, телефон, полный адрес,
   индекс, город, способ доставки**; может отметить
   «Гравировка готова» (по позициям, чтобы частичная готовность
   и несколько часов корректно работали). Права менеджера
   на изменение статуса согласуются с ролью логиста.
6. Две независимые истины: `engraving_ready` и `shipped`.
   «Готово» **не означает «Отправлен»**. После готовности
   используется один проверенный Main Stage5 dispatch-чеклист
   с частичной отправкой, точной отменой, idempotency/replay и
   резервами. Отправка до готовности запрещена точечно, а не
   глобально блокирует незатронутые строки.
7. «Логистика» — **операционный список/карточка**, а не копия
   старой таблицы заказов/цеховых расчётов. Фильтры бренд,
   ожидает гравировки, готово, отправлено, срочно/просрочено.

### Доставка и деньги
- Способы доставки остаются **как в текущем Main**, без урезания списка.
- Отдельные структурированные данные KazPost:
  `recipient_full_name`, `recipient_phone`, `address_full`,
  `postal_index`, `city`; плюс `delivery_type`.
  Показать всё в одной логистической карточке, обеспечить
  копирование/экспорт. Заказчик и получатель могут различаться.
- UI прежнего «Комментарий к заказу» у нового клиента превращаем
  в логистические поля адреса; **не переиспользуем неструктурированное
  старое `orders.comment` как единственный адрес/индекс**.
- Способы оплаты нового клиента: **KASPI RED, KASPI GOLD,
  Рассрочка**. Прочие clothing-подсказки исключить из клиентского
  интерфейса; существующие накопительные payment/refund/debt
  транзакции Main сохранить. «Рассрочка» на этом этапе — метод
  оплаты, а НЕ самодельный кредитный график.
- «Обмен размера» → **«Обмен»**. Действующие безопасные
  return/exchange/cancel/physical intake workflows сохраняются,
  но работают с exact watch SKU (два цвета, механизм) и brand fence.

### Навигация
- Инфопанель Main остаётся; название «Цех» → «Логистика».
- Заказы/создание, Логистика, Товары, Остатки/операции,
  Отчёты, Финансы/Касса — единый человеко-понятный watch UI.
- Не показывать clothing-поля, цеховые выплаты/задолженность,
  KPI по шапанам, старые проблемы как обязательный ежедневный раздел.

## 2. Техническая граница

Использовать последнюю проверенную Main source-lineage как базу;
сохранить Client3-specific FIRST ADMIN bootstrap/config из изолированной
ветки. Требуется explicit `CLIENT3_WATCH_TENANT` deployment gate
и ЕДИНСТВЕННЫЙ D1 binding с ID `0717f239-6d81-4837-8586-777d94e22c53`.
Нельзя создавать новую копию клиентской БД, очищать существующую или
предполагать, что она по-прежнему пустая (после октября могли начать работать).

**Предлагаемая аддитивная модель (до миграции уточнить реальную D1):**
- `watch_brands(id,code,display_name)`;
- `watch_products(catalog_product_id,brand_id,display_model_name)`;
  внутреннее legacy имя каталога уникально, но НЕ является моделью на UI.
- `watch_variants(catalog_variant_id,mechanism,bracelet_material,
  dial_color,bracelet_color)`; уникальный бизнес-ключ
  (brand/model/gender/mechanism/bracelet_material/dial_color/bracelet_color).
  **Критический предварительный шаг:** проверить существующие
  legacy SKU-uniqueness/resolver paths. Если они запрещают
  разновидности по механизму или ремешку, требуется client3-only
  canonical watch resolver; запрещено скрыто кодировать watch dimension
  в `length` или `size`.
- `orders.brand_id`, `orders.urgent`, `orders.dispatch_due_at`;
  отдельная `watch_order_delivery` с полями KazPost (не ломать старый комментарий).
- `watch_engraving_jobs` на order_item, immutable SKU,
  engraving_text, pending/in_progress/ready, ready_at, actor.
- `managers.brand_id` (у менеджера ровно один активный бренд),
  админ выбирает доступные. `cash_register_entries.brand_id`/
  separate opening balance; обеспечить brand-scoped all finance paths.
- Фиксировать бренд, SKU и атрибуты в snapshots каждой продажи/
  возврата/обмена; не меняем исторические цены при правке каталога.

## 4. Неподтверждённые нюансы — безопасные значения по умолчанию

- Браслетный цвет обязателен при «Кожа», пока для остальных материалов
  не задан новый бизнес-список.
- Для одного заказа может быть несколько надписей: данные по позициям;
  при `qty>1` и разных надписях — отдельные строки.
- «Срочно» автоматически сортирует логистику по deadline; после
  дедлайна показывает «Просрочено», **не отправляет автоматически**.
- Офис/Витрина — физические точки хранения, а не разные кассы;
  кассы разделены по брендам, не по источникам.
- Цены/долги/возвраты денег основываются на платёжном ledger,
  а не на смене статуса готовности гравировки.
