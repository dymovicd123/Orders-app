# P0 #648 — согласование схемы orders / order_manager_audit

Статус: **подготовлено к ручному рассмотрению; никакой D1 не проверялась и не менялась этим PR**.
Ветка: `fix/branch2-p0-schema-reconcile-and-preflight-20261030`, draft [#649](https://github.com/dymovicd123/Orders-app/pull/649).

## Подтверждённый дефект

При применении всех 114 существующих SQL-миграций к пустой SQLite Worker не может полностью воспроизвести текущую рабочую схему: нет `orders.manager_snapshot_name` и таблицы `order_manager_audit`.
Первое ломает HTTP Create с ошибкой 500; второе прячет невыполненную запись журнала менеджера за обработанным исключением. Зелёный HTTP-тест до #649 использовал явно объявленные локальные два дополнения схемы — **не production-миграцию**.

## Безопасное решение

`scripts/order-manager-schema-reconciliation-20261030.mjs` только инспектирует метаданные SQLite и возвращает **точный план SQL**, но **не содержит исполнителя и не обращается к облаку**:

- Если `orders.manager_snapshot_name` отсутствует, предложить `ALTER TABLE orders ADD COLUMN manager_snapshot_name TEXT`. Если уже есть — ничего не делать.
- Если `order_manager_audit` отсутствует, предложить добавление таблицы с полями, соответствующими Worker. Если таблица существует и содержит все поля и PK — ничего не делать. Если существует в несовместимой форме — **остановиться** и отдельно согласовать миграцию без утраты исторических событий.
- Никаких удалений, замены таблиц, переписывания заказов, изменения остатков, массовой синхронизации или автоматического применения.
- Эти SQL выполняются только после отдельного разрешения и селективного preflight на конкретной D1; не запускать подряд всю цепочку миграций на существующей D1.

Проверено на disposable SQLite с 114 миграциями: нет объектов, отсутствует только один из них, всё уже существует, несовместимая таблица, сохранность заказов и старых строк аудита. Тот же план используется **только внутри локального HTTP fixture**.

## Точные этапы до любого релиза

1. Сверить `wrangler.jsonc` и фактическое окружение: Branch2 Worker `orders-app-branch2`, D1 `orders_db_branch2_mirror_20261027`. Не путать со старой `orders_db_branch2` или production.
2. По отдельному согласованию запустить **read-only** аудит. В PR GitHub Action выполняет только локальные статические проверки; удалённое чтение допускается исключительно для ручного `workflow_dispatch` с `branch2` и только после регистрации нужной версии workflow в default branch (GitHub требует присутствия dispatch workflow в default branch). **Пока такой способ запуска не подтверждён, не утверждать, что remote D1 уже проверена, и не использовать workflow push как обход этого ограничения.** Скрипт допускает только GET metadata или POST одного `SELECT`, сверяет exact target ID и выводит лишь метаданные/агрегаты без клиентских строк. Если отдельный ручной запуск недоступен, оформить отдельную согласованную read-only процедуру перед релизом.
3. Сохранить описание структуры обеих баз, число строк аудита и orders. Не предполагать заранее, что продовая таблица отсутствует.
4. До любых SQL-записей получить D1 Time Travel bookmark/проверяемую резервную копию, определить rollback и утвердить конкретную целевую базу. Первой рассматривать Branch2, не production.
5. Подготовить SQL **только для фактически недостающих объектов**, проверить точную структуру существующей таблицы и первичные ключи. Исполнить только после отдельного разрешения. Повторное планирование должно вернуть пустой список.
6. На том же окружении проверить HTTP Create/Edit/reservations/returns и аудит. Если нет совпадения по схеме, **остановить релиз**.
7. Только после отдельного подтверждения рассматривать Main и внешний Cloudflare native build pipeline.

## Стоп-сигналы

- Неизвестная база, ID или имя расходится с ожидаемыми → ничего не выполнять.
- Таблица аудита уже есть, но отсутствует хотя бы одно ожидаемое поле либо PK → нельзя `DROP`/`RECREATE`; отдельный аудит.
- Ветка содержит неслитые зависимости #637, #639, #642, #644–#647 → сначала точный план слияния без побочных действий.
- Green CI означает исправность disposable тестового кандидата, **не** факт проверки или корректировки D1.
