# Stage 5: единая отправка заказа (решение владельца, 2026-11-01)

**Статус:** архитектурный контракт для следующей реализации в Branch2, НЕ подтверждённая реализация; в Main ничего не выпускать. Рабочие операторы должны видеть нормальный заказ, а не отдельные технические системы «обычная отправка» и «отправить замену».

## Проблема доказана в текущем Branch2

- `OrdersTableSection` показывает основную кнопку «Отправки» даже при `shipping_status=sent`; она открывает план, который `order-shipment-plan` считает `closed`.
- `order-shipment-plan` исключает `pendingExchangeDispatchId` из общего чеклиста с причиной «Замена отправляется отдельно до объединения механизма».
- `OrderExchangeSection` просит «позже нажмите Отправить замену», таблица строит отдельную кнопку **для каждой** позиции; `App.markExchangeReplacementSent` POST `/api/exchanges/pending-dispatch/:eventId`, который работает независимо от `POST /api/orders/:orderId/shipping/dispatches`.
- Глобальный `shipping_status=sent` запрещает обычный selective dispatch, даже если после обмена появились новые неотправленные позиции. Для нескольких замен нельзя считать одну из этих кнопок общей операцией.
- Картинки истории/проблем не должны становиться ежедневными обязательными маршрутами сотрудников.

## Один операторский стандарт

1. У заказа есть **одна** контекстная операция «Отправить товары» — только если есть хотя бы одна ещё не выданная готовая позиция. Она действует даже если исторически заказ `sent`, но после обмена появилась новая ожидающая замена.
2. Один чеклист показывает все доступные строки: обычный товар, новую замену после обмена, готовую позицию цеха. В каждой строке: товар, цвет/материал/размер, источник, `отправлено/осталось/готово`, выбор шт. По умолчанию отмечены доступные ещё не отправленные вещи. Для нескольких замен — **одна транзакция/одно подтверждение**, а не N независимых кнопок.
3. Неготовые, ещё не распознанные и без свободного резерва позиции остаются видимыми, но не выбираются; короткая конкретная причина и действие в контексте заказа.
4. После полной отправки без новых ожидающих строк основная кнопка **исчезает**. Просмотр старых выдач — второстепенное действие «Отправленные товары» в карточке/меню заказа, не ещё одна отправка.
5. Статус заказа выводится из всей актуальной цепочки выдач: `Не отправлен`, `Частично отправлено`, `Отправлен` и `Отправка не уточнена` для старых недостаточно доказанных фактов. Готовность цеха не значит отправку; фактический возврат не запрещает выдавать независимую оставшуюся позицию.
6. Одинаковый эндпоинт/доменных инвариант для обычных строк и новых строк обмена. Exchange сохраняется как **происхождение** новой строки, а не отдельная технология отправки. Нельзя реализовать единство только подменой заголовка при двух независимых транзакциях.
7. Единый учёт штучного количества и immutable события: строгий item/source/variant, active reserve, sale/dispatch lineage, requestId. Часть 1 из 3 должна сохранить два независимых факта: отданную 1 и ожидающие 2. Повтор, два менеджера, замена того же SKU и потерянный ответ не могут создавать вторую выдачу.
8. Исправление отправки касается **конкретного события/строки**, не всего заказа. После более поздней ревизии количество не восстанавливать автоматически; ранее проведённый частичный возврат либо обмен другой позиции не является глобальным запретом.
9. Старые `shipping_status`, legacy handover, fulfilled reservations, exchange lifecycle и returns не переписывать ради красивого UI. Ввести строго проверяемую совместимость, блокировать только небезопасное конкретное действие; миграция при необходимости — отдельно и только на тестовой D1.

## Приёмка перед новым релизом Branch2

- Старый полностью отправленный заказ: нет главной отправки, история доступна.
- Частично отправлено: только оставшиеся, количественно точно; одиночная выдача 1 из 3; затем 1 из 2; затем последняя; все повторы идемпотентны.
- Старый `sent` + новая **одна** замена: она в обычном чеклисте; без повторной отправки исходных товаров.
- Старый `sent` + **две/три** замены из разных источников: одна согласованная выборочная отправка; суммарные движения/резервы точно соответствуют строкам.
- Обмен `уже отправили` фиксирует ту же каноническую выдачу, `ещё не отправили` не двигает stock; Workshop ready-but-unsent также не двигает stock.
- Частичный возврат одной строки, повторная отправка другой, отмена только последней выдачи, поздняя ревизия, отказ при недостающем резерве и конкурентная выдача двух менеджеров.
- Нативный Worker + изолированная D1, чтение физических и финансовых следов; затем настоящая UI-проверка менеджером на Branch2. Все исправления Stage5 в Main запрещены до приёмки и явного решения владельца.

## Отдельно: Main Resolver (только диагностика, без записи)

`catalogReviewBasePredicate` включает строки с пустым `product_id` или `variant_id` и некоторые старые статусы; одно лишь наличие слов в справочниках не доказывает существование одного активного SKU. `catalogReviewOperationalPredicate` дополнительно показывает старый активный неотправленный заказ с действующим unresolved резервом, поэтому в списке могут быть записи сентября. Диагностика exact product+category+gender+color+material+length+size, алиасов, 0/1/N вариантов, status и истории заказа нужна **по конкретным строкам**. Автоматом привязывать только единственный доказанный активный SKU при отсутствии конфликтов исходной истории; неизвестное/неоднозначное оставить как конкретный вопрос. Не массово создавать SKU, не корректировать физику и не удалять резервы. Исторические проблемы — отдельная административная диагностика, не ежедневные задачи магазина.
