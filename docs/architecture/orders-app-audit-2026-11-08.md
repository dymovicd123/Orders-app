## Чёткие критерии завершения очистки — без бесконечного дробления

Работа не считается завершённой только потому, что отдельные SQL-функции вынесены. Закрыть по нижеследующим проверяемым условиям, не делая PR ради количества строк:

1. **Домен Return/Exchange:** создание, отмена, деньги, физическая приёмка и Цех локализованы в предметных модулях; публичные маршруты стабильны; последние этапы `createExchange` / `cancelExchange` / Exchange Set V2 проходят реальный HTTP/SQLite и finance gate без циклических зависимостей.
2. **Frontend:** `src/App.tsx` имеет выделенные предметные оркестраторы отправки/возврата/обмена с точными типами и понятными контрактами; статусы, кнопки и история проверены по реальному набору старых, новых, частичных и последовательных операций. Не ставить целью произвольную длину файла.
3. **CI и история:** 28 исходных кандидатов на пересмотр тестов классифицированы на актуальные/дубликаты/архив с доказательством сохранённого покрытия; obsolete workflows не запускаются; обязательный `release:check` и сборка проходят. Не удалять тесты и фикстуры без проверки их использования.
4. **Контроль безопасности:** никаких неожиданных D1 миграций или writes к Production; точные связи Production/Branch2 подтверждены; реальные CAS/idempotency, Physical/Reserved и финансовые события не регрессируют.
5. **Приёмка:** ручные браузерные сценарии для статусов отправки, возвратов/обменов/отмен, Цеха и старых заказов пройдены в изолированном окружении; результаты записаны в этом аудите. Зелёный CI не равен выполненной браузерной приёмке.

**Правило остановки:** после выполнения всех пяти пунктов перестать выносить код без доказанного сопровождательного выигрыша, продолжить функциональную разработку. Отдельно оставлять неопасные долговые пункты с приоритетом и владельцем, а не считать их причиной бесконечной очистки.

## Что структурно не так

1. **Смешана ответственность.** `App.tsx` одновременно оркестрирует разделы, состояние, API-запросы, редактирование заказов и складские диалоги. `worker/index.ts` сочетает auth/HTTP/валидацию/операционную логику большого числа маршрутов.
2. **Слишком широкие доменные файлы.** `returns-exchanges.ts` содержит возвраты, обмены, денежные события и инвентарный жизненный цикл; `order-reservations.ts` — допуск резерва, ревизии и выдачу. Изменения для одного сценария задевают другой.
3. **Границы модулей недостаточно типизированы.** UI-компоненты получают большой `ctx` с `any`, а `OrdersTableSection` отключает TypeScript. Это мешает компилятору обнаружить несовместимость.
4. **Статус заказа имеет несколько источников.** Историческое поле `shipping_status`, события `order_dispatch_items`, складская выдача и статусы обменов сосуществуют. Требуется один read-model, который проектирует статус по фактическим событиям; до этого нельзя удалять старые маршруты.
5. **CI накоплен как история релизов.** Есть отдельные одноразовые workflow, привязанные к конкретным PR, веткам, датам и SHA; наряду с ними живут общий `Quality check`, модульные acceptance workflow и 354 `test-*`. Историческая проверка иногда проверяет буквальную форму старого исходника вместо инварианта поведения.

## Порядок исправления

### P0. Устранить ложные красные и закрыть опасные релизные лазейки

- Не менять текущие права менеджеров ради исторического теста; обновить тестовую спецификацию согласно действующей политике.
- Заменить хрупкие `source.includes(...)` в критичных местах на AST или реальные Worker HTTP/SQLite тесты.
- Убрать завершенные одноразовые workflow из активной директории; сохранить историю в Git и документах.
- Отдельно проинвентаризировать все старые production-migration и `workflow_dispatch` workflows: ни одна забытая команда не должна иметь возможность применить прошлую миграцию повторно.

### P1. Разделить тестовый фонд по назначению

- **PR required / быстро:** typecheck, build, core financial/shipping/reservation/return/edit invariants, без облачных записей.
- **Change-scoped:** backend/shipping, warehouse, returns-exchanges, finance, UI and roles tests запускаются по затронутым файлам; добавлять тест для пересекающихся сценариев.
- **Branch2 acceptance:** реальные HTTP + SQLite, Chrome, повторные запросы, параллельные действия, проверки всего order lifecycle; только безопасные параметры тестового Worker/D1.
- **Historical fixtures / archive:** старые снимки и точечные one-off проверки; не исполнять их на каждом PR без подтвержденного текущего контракта.
- Для каждого теста документировать `owner`, `purpose`, `runtime`, `required/nonrequired`, `fixtures`, `last review`. Удаление дублей — только после определения покрытия.

### P2. Рефакторинг тонкими вертикальными срезами

1. **HTTP**: вынести маршруты `/api/orders/:id/shipping/*` из `worker/index.ts` в `worker/routes/order-shipping.ts` без изменения SQL/ответов. Затем аналогично маршруты возвратов, обменов и склада.
2. **Domain**: разделить `returns-exchanges.ts` на `returns/`, `exchanges/`, `intake/`, `financial-settlement/` с общими маленькими функциями, не перемещая ответственность за ledger в UI.
3. **Reservations**: отделить `reservation-admission`, `stocktake-handover`, `physical-dispatch` и `correction`; обмены и возвраты должны работать через общие инварианты движения товара.
4. **Frontend**: переносить orchestration из `App.tsx` в typed controller hooks по рабочим разделам; постепенная замена `ctx: Record<string, any>` на явные интерфейсы; снять `@ts-nocheck` только после прохождения typecheck.
5. **Inventory**: разделить `InventorySection.tsx` по view + action/controller; отдельно операции, остатки, ревизии, приход, статистика. Не копировать логику по компонентам.

Цель — файлы с одной ответственностью; условный ориентир нового модуля 200–600 строк. Ограничивать размер PR и проверять, что для менеджера UI/поведение не меняются при чистом извлечении кода.

### P3. Зафиксировать контракт жизненного цикла заказов

Минимальная матрица: 1/3/все отправлено; 0 свободного остатка с подтверждением фактического товара; старый fulfilled без повторного списания; инвентарная ревизия до/после заказа; exchange replacement; частичный и полный возврат; отмена отправки; конкурентное изменение; повтор того же requestId; отличие склад/бутик/цех. Для каждого варианта проверять одновременно **статус строк, общий статус, резерв, склад, движения, финансы, действия интерфейса**.

## Правила выпуска после реорганизации

- PR -> обязательный зеленый набор, меняющиеся модули -> дополнительные тесты.
- Изменение складских/денежных транзакций -> реальный HTTP/SQLite acceptance и Branch2 до Main.
- Main deploy проверяет точный SHA и production конфигурацию, не меняет D1 без отдельного согласованного migration process.
- Нельзя объявлять релиз полностью проверенным, если хотя бы одна относящаяся к нему required-проверка красная.
- «Чистый рефакторинг» запрещает изменение бизнес-ответов и SQL без отдельного PR и отдельного объяснения.

## Что этот аудит НЕ доказывает

Размер файлов не равен количеству логических ошибок, а список из 354 тестов сам по себе не означает, что 354 независимых теста реально выполняются. Для массового удаления/переноса нужны граф зависимостей тестов и подтверждение текущих контрактов. Прохождение CI не заменяет выборочное ручное тестирование сложных транзакций в изолированной среде.
