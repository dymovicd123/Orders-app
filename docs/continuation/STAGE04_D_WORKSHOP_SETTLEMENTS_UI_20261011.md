# Stage04-D — единая вкладка «Расчёты с Цехом» (2026-10-11)

## Решения клиента

- Обычные заказы и Kaspi выполняет один цех, общие расчёты.
- Оплату стараются проводить в день готовности/получения изделий; непогашенная сумма накапливается.
- Авансы не нужны; никакого случайного превышения подтверждённого долга.
- Стоимость работы определяется **себестоимостью соответствующего варианта из каталога на момент готовности** (Stage04-B2). Отсутствующая цена остаётся неизвестной.
- Начальная задолженность будет согласована отдельно непосредственно перед запуском, без начисления истории заново.

## UI

В существующем «Цех» третья соседняя вкладка «Расчёты с Цехом» только для администратора. Обычные и Kaspi очереди продолжают работать без изменений. Компонент изолирован: `src/features/workshop/WorkshopSettlementsPanel.tsx` и `src/styles/stage04-workshop-settlements.css`.

Раздел содержит:
- единый накопленный долг, сегодня готово, сегодня выплачено, количество работ без подтверждённой себестоимости;
- разрез по дням с реальным остатком на начало периода и переносом долга;
- удобную отдельную форму выплаты (сумма, способ оплаты, комментарий), предупреждение о превышении долга, повторная отправка с устойчивым idempotency key;
- историю начислений и выплат с безопасной отменой ошибочной выплаты (причина сохраняется);
- список готовых изделий, у которых отсутствовала себестоимость при начислении.

До запуска вместо вводящих в заблуждение нулей финансовые KPI показывают прочерк и объяснение режима подготовки. Кнопки финансовых записей отключены, пока `workshop_settlement_capture_control.enabled=0`.

## Коррекция неизвестной себестоимости

Новые admin-only маршруты:
- `GET /api/workshop/settlements/unpriced`
- `POST /api/workshop/settlements/unpriced/:completionId/confirm-cost`

Позиция может быть подтверждена **только по существующей себестоимости каталога**, если одновременно совпадают связанная позиция заказа/товар/вариант, характеристики, статус «готово» и количество с замороженной записью завершения. Любое расхождение оставляет вопрос в очереди для ручной сверки. Подтверждение создаёт отдельный `price_adjustment` с `related_event_id`, не изменяя предыдущие записи. Повторы идемпотентны. Отмена готовности после корректировки должна компенсировать итог с учётом этой корректировки через существующий Stage04-B reversal trigger.

Ежедневный итог «Выполнено» включает также подтверждённые после первоначальной готовности себестоимости, по дате подтверждения, не переписывая дату старой готовности.

## Граница запуска

**Stage04-D = готовый интерфейс и серверные маршруты, но ещё не бизнес-активация.** Требуется до cutover:
1. Согласовать точный начальный долг на одну дату и проверить занесение начального баланса в отдельную неизменяемую запись.
2. Проверить себестоимость каталога по активной продукции, включая список без цены.
3. Согласовать, как отражать выдачу денег цеху в основной кассе/финансовом отчёте, чтобы не возникло двойного списания; Stage04-C специально отделён от customer payments.
4. Отдельно протестировать сценарий готовность → начисление → выплата → долг → возврат в работу на изолированной Branch2 D1.
5. Только после этого согласованно включить capture, затем подготовить отдельный production выпуск. НЕ включать автоматически при PR merge или публикации.

Текущий PR затрагивает только `branch2`. Нет изменений production/ main D1, старых заказов, платежей, статусов и складских остатков. Исторический регрессионный тест исполняется без изменений на замороженном baseline, после него обязательна пересборка текущего frontend с новым UI.
