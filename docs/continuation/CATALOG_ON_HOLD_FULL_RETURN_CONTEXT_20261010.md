**Контрольная точка:** 10 октября 2026, branch2 `68eacdf25404dcca98d7839961e601d2455a0dcc` (после PR #365).  
**Важнейшее:** функция справочников **не считается полностью завершённой**. Мы сознательно ставим дальнейшую разработку на паузу и после релизного аудита возвращаемся к Stage04, затем Stage05. Не превращать «пауза» в «всё завершено».

## 1. Что согласовал владелец

- Справочники нужны для нормальной самостоятельной работы клиента после ухода разработчика: нельзя заставлять обращаться к программисту для чистки ненужных цветов/материалов/значений, поиска дубликатов, объединения и управляемых исправлений.
- **Источник истины выбирает администратор**, не алгоритм, не количество остатков, не дата создания. Это касается и названия справочного значения, и конкретного SKU.
- При правке городов/доставки/способов оплаты затрагивать **актуальные заказы текущего месяца** по защищённым контрактам; старые месяцы — история; финансовые факты и суммы не переписывать по умолчанию.
- Для причин возврата и списания изменить будущий выбор, **не переписывать текст уже оформленных операций**.
- Сохранить реальный физический склад и бутик отдельно, активные резервы и все клиентские обещания. Отрицательная или нулевая физика не разрешает автоматически аннулировать заказ.
- Операции объединения/исправления редкие администраторские, работники не должны получать долгую блокировку текущих заказов.
- Общий **редизайн** всех операций (особенно **списания**, затем объединения, обменов/возвратов, цеха, ревизии) и личная визуальная приёмка владельцем — **после Stage04 и Stage05**. Приход пока без решения по новому UI.
- **Stage04** — расчёты с цехом; **Stage05** — экономика, себестоимость, маржа/прибыль/аналитика, НЕ редизайн.

## 3. Невыполненное: разные реальные характеристики SKU

**Не путать нормализацию названия цвета со сменой физической идентичности.** `ХАКИ` → `ЗЕЛЁНЫЙ` может означать синоним в справочнике, ошибку карточки товара либо физически другую вещь; изменение цвета, размера, материала, длины, возраста ребёнка — не всегда безопасное «переименование».

Текущее: сервер отдаёт `unique_keeper`, `no_keeper`, `ambiguous_keepers`, `needs_execution_review`, `historical`, stock/reserved per location, active reservations/order lines, shortages. **Запись намеренно не реализована**.

### Бизнес-сценарии для будущего согласования
1. Источник и цель — синонимы, физически один и тот же товар: администратор отдельно выбирает keeper по каждому источнику SKU, система переводит безопасные активные ссылки с учётом месяца и состояния исполнения, а историю отгрузок не меняет.
2. Разные реальные товары: **не объединять SKU**; можно исправить только справочник будущего выбора либо выполнить явную отдельную корректировку неверного атрибута после физической сверки. Никакого автоматического переноса.
3. Keeper отсутствует: предложить создать корректный вариант у правильного товара и исполнения, но не создавать невидимый дубль.
4. Несколько keeper-кандидатов: не угадывать; человек выбирает один с понятной карточкой и подтверждением.
5. Архивный SKU: не оживлять по умолчанию; учитывать старые документы, устаревшие ссылки/переходы.
6. Два физических учёта одной вещи: сложение запасов запрещено без независимой проверки; допустимые варианты решений по каждой точке — sum/keep_source/keep_keeper/physical_count/defer с evidence.
7. Резервы/заказы: сохранять открытые обещания, не уменьшать их и не менять цены/денежные факты; дефицит выводить явно.

### Как проектировать writer после возвращения
Отдельная именованная операция, не обычный `consolidate-unused`. Для каждого source SKU нужны: `keeperId` либо `create/keep-separate/defer`; решение warehouse/boutique, проверка действующих заказов/резервов, статуса цеха/возвратов/обменов/ревизий/приходов/перемещений; snapshot/canonical identity; CAS-token всех затрагиваемых данных; immutable receipt, postconditions внутри **одной D1 транзакции**; повторная проверка перед записью; отказ при любых неизвестных конфликтах и понятный пользователю план исправления; безопасная идемпотентность/replay. Отдельные тесты на гонку между preview и commit, старые и будущие месяцы, двойные резервы, stock shortages, active workshop, архив, два склада и отмену связанных операций.
**Никакой универсальный cross-characteristic writer пока не включать без согласования семантики клиента.**

## 4. Невыполненное: сложная отмена после последующих операций

После объединения могут пройти: продажи, отправки, оплата, обмен, возврат, приход, ревизия, перемещение, списание. «Просто вернуть старые SKU и количество» создаст дубли или уничтожит реальный товар.

**Нужен workflow разрешения случая, а не глобальная кнопка отката**:
1. В админском разборе открыть immutable consolidation receipt и связанные последующие события по страницам;
2. Построить provenance для активных резервов/заказов и физического stock по точкам; различить untouched объекты (у них возможен уже реализованный safe undo) и изменённые;
3. Предложить корректирующие действия (оставить историю, компенсировать ошибочный резерв, пересчёт в нужной точке, восстановить только незавершённый документ, etc.), не удалять shipped history;
4. Require per-action confirmation/admin reason, CAS, audit trail, idempotent recovery; не возвращать client refunds/payments без отдельной финансовой операции;
5. Прогнать сценарии продаж, отмен, возврата в запас, обмена, позднего прихода/ревизии, склада/бутика, нескольких поколений merge/undo, race/cancel/replay.

Текущие `canAutomaticallyUndo:false` и `canMarkResolvedFromPreview:false` — правильная граница; не убирать её.

## 5. Другие известные ограничения

- Поиск дублей до 12k каждого вида возвращает честный `limited`, не обещает exhaustive discovery сверх предела. Если каталог реально превысит 12k, сделать отдельный cursor-based export/resumable scanner.
- Долгие блокировки штатных сотрудников запрещены; все большие проверки read-only, запись краткая и атомарная.
- Work визуально подтвердил 4 прежние UX-ошибки на десктопе. **Новая сложная панель и 390px мобильная версия не прошли пользовательскую визуальную приёмку**. Перенести этот аудит на период после Stage04/Stage05, не утверждать обратное.
- Редизайн списания **обязателен**, а интерфейс всех остальных операций пересмотреть после Stage04/05. Приход отдельно согласовать.

## 6. НЕОБХОДИМАЯ регрессия после справочников и перед main

**Проверять реальный новый runtime, а не только frozen baseline.**

Области:
- Заказ: создание/редактирование/удаление, способ оплаты, Kaspi-магазин, отправка/сохранение старого SKU, цены/долг/предоплата, разбор устаревшего source SKU;
- Склад: приход в уже объединённый/архивный вариант, движение и отмена движения, резерв/разрез warehouse/boutique, списание с shortage, ревизия, перевод;
- Цех: активная задача, готовность, накладная, Kaspi/обычный, отсутствие самостоятельного начисления Stage04 при выключенном capture;
- Обмен/возврат: полный/неполный приход, разные товары/цены, фактическое возвращение в остаток, старые привязки к merged SKU, деньги по способу оплаты;
- Финансы и отчёты: касса, переплата/возврат, отчёт по дате оплаты Kaspi, день, старый документ, `legacy_manual_total` vs `itemized_v1`;
- Permissions: CRUD/merge only admin, обычные операции работников не блокированы;
- D1: backup/read-only fingerprints, сравнить число заказов/оплат/stock/reservations до/после миграций, FK, триггеры, reserved consistency;
- CI/Deploy: Quality, Stage04-safe, active runtime cross-domain tests, Cloudflare exact public JS, security audit, user smoke.

**Ловушка существующей проверки**: `scripts/catalog-integrity-branch2-preserved-gate.mjs` тестирует новые catalog/reference сценарии на текущем коде, а затем **временно подменяет файлы на frozen Stage04 baseline** для старой большой `release:check`. Так обеспечена обратная совместимость baseline, но это **не эквивалент** полного smoke всех действующих операций на новом runtime. Перед Production нужен отдельный cross-domain e2e/SQL test suite на реальном branch2 runtime. Не ослаблять frozen guard; запустить оба.
