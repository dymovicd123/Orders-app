# Stage04-B3 / D3 — восстановление себестоимости при заказе без variant_id (2026-10-11)

## Факт из тестовой Branch2 D1
По запросу пользователя проверено единственное незакрытое начисление на готовый товар «АЙ-НӘЗІГІМ КӨЙЛЕК».
Отсутствовала привязка к SKU **в обеих** существующих записях: `order_items.variant_id IS NULL`, `workshop_tasks.variant_id IS NULL`.
Само задание / order_item / frozen completion согласованы по order id, количеству, названию и всем сохранённым характеристикам. Цена была назначена в каталоге, но чтение финансового журнала делало `cv.id=COALESCE(oi.variant_id,wt.variant_id)`, получая NULL и ложное «Требуется сверка товара».
Отдельное чтение D1 (без записи данных и без публикации цен/идентификаторов заказов) подтвердило: **три активные вариации** исходного товара, **ровно одно совпадение** сразу по цвету, размеру, материалу, длине и полу и одна заполненная себестоимость для совпадающего SKU.

## Исправление
`worker/domains/workshop-settlement-prices.ts`: только для старого заказа без обоих variant_id, при наличии корректного связанного `order_item_id` и `product_id`, находим ровно один активный вариант этого продукта, совпадающий со всеми пятью замороженными характеристиками `details_snapshot`. Ищем полный SKU по *COUNT(*)=1*, не выбираем случайный первый товар. Если хотя бы один атрибут не совпал, нет связанного order_item/product, вариант неактивен либо есть дубликат, оставляем `needs_match` и не начисляем ничего. Старые данные товара, заказа, цеха и журнала не правим.
Цена по найденному `stock_position_id + category` с отдельной записью `price_adjustment` на дату подтверждения администратором; исходный `completion` остаётся неизменным. Повтор запроса безопасен.

`migrations/0108_v72_workshop_unique_legacy_sku_pricing.sql`: аналогичная уникальная проверка для **будущих переходов в «Готово»** в Branch2 D1, чтобы новая готовность такого legacy заказа с известной себестоимостью могла начисляться сразу. Этот SQL только заменяет триггер; не меняет флаг capture, не делает backfill и не затрагивает старые финансовые события. Reversal trigger остаётся неизменённым.

## Проверки / безопасность
- Тесты проверяют уникальную цену, заморозку финансовых событий, корректировку старой записи, недопустимость повторов, неоднозначный SKU, неправильный цвет, другой order и возврат в работу.
- Гейт historical release: SHA-pinned миграция скрывается только на время замороженного исторического тестового дерева, текущие Stage04 тесты остаются активными.
- Workflow `stage04-branch2-migration-0108.yml` устанавливает триггер лишь в `orders_db_branch2` и сравнивает численности и финансовые суммы до и после, подтверждает `capture=1`. Никакого main или production D1.

## Как проверить после выкладки
Открыть Цех → Расчёты с Цехом → Без себестоимости → Обновить. При успешной загрузке система покажет **себестоимость** и кнопку **«Подтвердить начисление»**, больше не «Требуется сверка товара». После подтверждения одна `price_adjustment` увеличит долг на себестоимость × количество, а исходная завершённая позиция исчезнет из очереди. Стоимость назначается только администратором. Не нажимать «Подтвердить» до проверки показанной суммы.
