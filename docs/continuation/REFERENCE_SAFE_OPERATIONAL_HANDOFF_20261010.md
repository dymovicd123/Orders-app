## Приоритет и граница

Заказчик попросил довести функциональную безопасность справочников сегодня и **завтра продолжить Stage04 (расчёты с цехом)**. Stage05 — **экономика/прибыль/аналитика**, не редизайн. Общая UX-приёмка лично заказчиком и переработка интерфейсов операций, особенно списания, — **после Stage04 и Stage05**. Приход переделывать только после отдельного решения.

Не называть произвольное объединение разных физических SKU или отмену с поздними продажами «автоматически готовыми»: реальные товары и клиентские обязательства нельзя угадывать.

## Функционально сделано в справочниках

- Единый администраторский раздел справочников, CRUD, защищённое скрытие/удаление свободных значений, просмотр дублей, выбор основного значения и журнал изменений.
- Города/способы доставки: выбранное администратором основное значение, корректировка заказов **текущего месяца** с CAS и аудитом; предыдущие месяцы остаются историей.
- Способы оплаты (ТЕРМИНАЛ → KASPI PAY и другие допустимые безналичные): текущий месяц и связанные финансовые записи, без переписывания сумм/дат/кассы/Kaspi-магазина и старой истории.
- Причины возврата/списания: PR #360/#361, миграция 0105 + защищённый writer; замена выбора для будущих операций, неизменность старых комментариев/возвратов/списаний, audit + SQL validation. Schema 0105 в isolated branch2 проверена.
- Идентичные SKU: выбор keeper исключительно администратором, не по количеству; детальный предпросмотр заказов/резервов/склада+бутика, серверный CAS, атомарный журнал/stock+order final proofs; нет фиктивного списания.
- PR #362: проверка дублей справочника и каталога **постранично по ID** через 400 записей за раз, не обрывается на бывшем пороге 1500/2000, единая группировка на всех прочитанных страницах. Верхний предохранитель 12000 записей *каждого* вида, после которого `limited/skuLimited` и реальные счётчики явно говорят, что поиск НЕ исчерпывающий. Нет долгих блокировок работников.
- PR #363/#364: полноценные **выбираемые по каждой точке решения по физическому товару для идентичных SKU**: (1) sum только при физических разных экземплярах, (2) keep_source, (3) keep_keeper, (4) physical_count с вводом реального подсчёта, (5) defer без изменения. Ничего не предвыбрано. Требуется явное подтверждение каждого места; для количественных исправлений — объяснение не менее 12 символов. Клиентский helper fail-closed проверяет остатки, резервный минимум и параметры; **сервер повторно проверяет** идентичность, резерв, обратимые операции и token при атомарной записи, с журналом ревизионной корректировки, а не мнимой продажей. Работа доступна лишь admin в `branch2`.
- PR #353/#357/#359: read-only полная курсорная карта **разных характеристик** (цвет/материал/длина/взрослые размеры/детские возраста), включая остатки, резервы и открытые заказы обеих сторон, дефициты, неоднозначные/архивные случаи, без лимита 400 вариантов, ошибочное самосопоставление отклонено.
- Механизмы некоторых узких безопасных compensated undo/remerge SKU уже покрыты тестами (нулевой, отдельные untouched резерв/положительный остаток по контрактам). Сложные случаи с поздними операциями имеют полноценные read-only case review, пагинацию и план разбора.

## **Намеренно НЕ разрешено** (не выдавать за реализацию)

1. **Объединение разных реальных характеристик активного физического товара**. Два цвета, разные размеры/возраста/ткани/длины могут быть *разными товарами*, а не орфографическими дублями. Карта только помогает решить. **Никакой универсальный cross-characteristic writer, переприсвоение текущих SKU, складское сложение или изменение customer obligations не включены.** Нужен отдельный business contract и именной явный план для каждого SKU/склада/бутика, отдельный immutable receipt, CAS, выверенные действующие обязательства/исторические snapshots и полномасштабная проверка. Самовольная автоматизация запрещена.
2. **Универсальная отмена объединения SKU после новых продаж, отправок, обменов, возвратов, перемещений и ревизий**. Историю не «откатывать». Использовать Case review/workplan и штатные корректировки только после проверки текущей реальности. Обещание кнопки «Отменить всё» недопустимо.
3. Порог 12000 при редком огромном справочнике: результат маркируется **неполным**; нельзя делать вывод «дублей нет». Разработка отдельного экспорта/long-running сканера только при практической необходимости.
4. **Общая UX-ревизия всех рабочих операций**: после Stage04/Stage05, включая обязательно списание, объединение, обмен/возврат, цех, ревизию. Приход ждёт отдельного решения.

Эти пункты — **оставшиеся продуктовые ограничения**, а не скрыто завершённые работы. Их не переносить на `main` и не разрешать без подписанного согласования бизнес-последствий. Ни в одном новом frontend-PR #362–#364 не добавляли менее строгий серверный writer.
