# Stage04 — включение автоначислений в тестовой Branch2 (2026-10-11)

## Цель

По запросу владельца проекта активировать уже реализованное начисление оплаты цеху, **только в тестовом окружении Branch2**, для проверки всей цепочки: новая готовность -> начисление по себестоимости -> частичная выплата -> долг -> исправление.

## Что происходит при активации

Контрольная запись `workshop_settlement_capture_control` в **изолированной D1 `orders_db_branch2`** переводится из `enabled=0` в `enabled=1`, а `activated_at` фиксируется временем самой операции. Никаких миграций/изменений в `main`, production D1 или боевых финансах. Это **настоящая запись в тестовой D1**, а не фиктивный фронтенд.

Автоматическое начисление сработает лишь на **новый** переход позиции цеха из рабочего статуса в `ready/done`. Уже готовые до активации товары **не пересчитываются автоматически** и стартуют без исторического долга. После запуска можно использовать существующие активные позиции: когда они впервые перейдут в готовность, начисление появится в общей тестовой вкладке. Если старую готовую позицию сознательно вернуть в работу и затем снова отметить готовой, это будет новое изменение статуса и создаст новое начисление; не используйте старые реальные позиции для такого теста без понимания последствия.

Цена берётся из текущей `catalog_execution_prices.cost_price` через точный SKU+категорию. Если цены/совпадения нет, создаётся запись без стоимости, попадающая в очередь `Без себестоимости`. Неизвестная цена не равна нулю.

Выплата тестовая: вносится в отдельный журнал цеха; **не списывается с основной кассы магазина** и не отражается в платежах клиентов. Не выдавайте реальные деньги на основании тестовых сумм. Вся история Branch2 остаётся отдельной от основной.

## Строгие защитные условия

Одноразовый workflow `.github/workflows/stage04-branch2-enable-test-capture.yml`, выполняемый **только при его первом попадании в branch2**, проверяет:
- branch2/Worker `orders-app-branch2` и D1 `orders_db_branch2`, UUID `40065052-854e-44b8-bcd5-251bdd488301`;
- состояние `enabled=0, activated_at=NULL`;
- пустой журнал начислений и выплат **до тестового cutover** (если он уже не пустой — требуется ручной разбор, включение остановится);
- установленный триггер Stage04-B2 с себестоимостью каталога, неизменяемость журнала, триггер компенсаций и поле способа выплаты 0107;
- полный набор изолированных тестов Stage04-A/B/B2/C/D.

Если любое условие не выполняется, не меняет управление. После переключения повторно читает состояние D1 и выводит дату cutover, число старых готовых позиций (только для информации) и количество финансовых событий.

## Как проверить

1. Откройте тестовый сайт https://orders-app-branch2.orders-clothes.workers.dev/ под администратором. В Цех -> Расчёты с Цехом должна исчезнуть надпись «Учёт пока не запущен».
2. На **тестовом** активном заказе с товаром из каталога перейдите в «Готово». В истории должно появиться начисление `себестоимость × количество` и увеличиться долг.
3. Создайте частичную выплату, проверьте новый долг и историю; при необходимости отмените тестовую выплату с причиной.
4. Отдельно проверьте товар без себестоимости: он должен попасть в очередь «Без себестоимости», без нулевого начисления. Восстановите себестоимость в каталоге, затем подтвердите стоимость.
5. Убедитесь, что у старых готовых позиций автоматического начисления нет.

## Остановка тестового начисления

При проблеме достаточно отдельным безопасным админ-действием выключить флаг `enabled=0` в **той же Branch2 D1**. Отключение **не удаляет** события; возвращение в работу после отключения по-прежнему создаст законную компенсацию предыдущей готовности. Не запускать такую процедуру на production и не удалять журнал.

## После приёмки

Начальное сальдо клиента, дата боевого cutover и объединение выплат с основной кассой остаются вопросами **для отдельного production-релиза**, а не для текущего эксперимента.
