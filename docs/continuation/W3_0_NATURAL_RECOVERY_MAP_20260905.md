# W3.0 — карта естественного восстановления склада

Дата: 2026-09-05

Статус: source-only audit завершён. Никаких изменений поведения Production, миграций или D1-запросов не выполнялось.

Точка истины для кода: `main` @ `1cf1f302dfbb8e7852bdbb0e3a3a5a5a7bd02d26` (`W2.1: fix Warehouse Attention refresh race`).

Этот файл живёт только в `context/project-continuation`, чтобы документация не запускала Production deploy.

## Цель W3

W3 — не развитие отдельного «центра проблем». Цель: **добровольное непрерывное самовосстановление склада**.

Порядок реакции системы:

1. Если уже известных фактов достаточно — исправить состояние автоматически.
2. Если не хватает одного простого физического факта — предложить дать его прямо в естественном рабочем месте.
3. Проверка должна быть добровольной, если без неё операция остаётся безопасной: `Не сейчас` / `Сейчас проверить не могу` — нормальный путь.
4. Если человек не может проверить товар (дома, в дороге, с телефона, спешит) — не запрещать обычную безопасную работу.
5. Только действительно неразрешённые вопросы остаются в `Нужно уточнить`.
6. Hard block допустим только там, где продолжение реально может повредить физическую правду/историю или невозможно однозначно определить объект операции. Причину надо объяснить человеческим языком.

Никакой геймификации, рейтинга сотрудников, обязательных квот проверок или психологического давления. Стимул — подходящий момент, несколько секунд и понятная польза для коллег.

## Классификация W3

- **AUTO** — система должна восстановиться сама.
- **INLINE OPTIONAL** — маленькая добровольная проверка прямо в текущем сценарии.
- **PARK** — безопасно продолжить работу, вопрос оставить на потом.
- **HARD BLOCK** — продолжение действительно небезопасно; блокировать только конкретную операцию/позицию и объяснить почему.

## 1. Создание и редактирование заказа

### Что уже хорошо

Обычная нехватка по Складу/Бутику не запрещает создать заказ. Backend `assertCreateOrderShortageDecisions` пропускает Цех и для обычного товара предлагает два пути: физически посчитать либо выбрать `Сейчас проверить не могу`.

Если менеджер добровольно вводит физическое количество, резерв и исправление физического остатка применяются согласованно; создаётся физическая проверка. Если он не может проверить — заказ всё равно сохраняется.

### Класс

- известный товар, нормальный остаток: **AUTO / ничего не спрашивать**;
- реальная нехватка, человек рядом с товаром: **INLINE OPTIONAL**;
- человек не может проверить: **PARK**, заказ сохраняется;
- неизвестная характеристика/товар: **PARK** для оформления заказа, структурная идентификация позже;
- Цех: не требовать складской проверки при создании заказа.

### Что улучшить позже

- Сохранять мягкий путь `Сейчас проверить не могу`; не превращать его в обязательную сверку.
- Убрать старую формулировку `Склад → Внимание`; W2 использует второстепенное `Нужно уточнить`.
- Не добавлять фоновую глобальную загрузку Attention ради одной подсказки.
- Не спрашивать повторно после добровольного отказа в рамках того же сценария.

### Соседние проверки

Создание, редактирование, повторный submit/idempotency, резерв, Workshop, availability UI, concurrent shortage, мобильный сценарий, secondary refresh failure.

## 2. Остатки

### Что уже хорошо

Карточка конкретного варианта уже содержит точечное `Сверить количество`. Это естественное место: человек сам открыл конкретный товар и уже видит `На месте / В заказах / Свободно`.

`Короткая проверка` на Overview запускается только явно кнопкой `Начать`; открытие `Остатков` само не тратит read на подбор cycle-count.

### Класс

- отрицательный физический остаток / свободно ниже нуля: **INLINE OPTIONAL**;
- обычный товар без сигнала риска: не беспокоить;
- пользователь сам открыл `Подробнее` и товар рядом: **INLINE OPTIONAL**;
- новая достоверная точечная сверка: **AUTO** должна сделать старую количественную неопределённость неактуальной, где это доказуемо.

### Лучший первый nudge

Использовать уже загруженную строку конкретного SKU, без глобального Attention и без нового списка задач. Например:

`Если товар сейчас рядом, можно за несколько секунд уточнить остаток. Это поможет другим менеджерам увереннее видеть наличие.`

Кнопки: `Уточнить` и спокойный выход `Не сейчас` / закрытие без последствий.

### Read-budget

Не вызывать автоматически `listInventoryCycleCountSuggestions`: подбор анализирует всю точку и движения. Для contextual nudge сначала использовать уже загруженные данные строки. Полный подбор остаётся только после явного `Начать/Обновить`.

## 3. Короткие проверки / Проверка

Backend уже имеет хорошие свойства: idempotency, CAS/freshness, запись совпадений и расхождений, возможность продолжить начатую большую проверку позже.

На Overview W2 рискованные строки используют blind-first, а безопасные допускают быстрый `Да, на месте X`.

### Найденная UX-несогласованность

В самой вкладке `Проверка` второй интерфейс короткой проверки показывает системное `На месте X` для всех рекомендаций. Это отличается от W2 Overview, где отрицательный free/предыдущее расхождение скрывают ожидаемое число до физического счёта.

Не P0 для W3.1, но при последующем объединении механизмов нельзя оставлять два разных принципа для одной и той же короткой проверки. Risk rows лучше blind-first; обычные добровольные проверки могут оставаться быстрыми.

### Класс

- короткая проверка: **INLINE OPTIONAL**;
- начатая пользователем полноценная ревизия: её собственные ограничения допустимы, но пользователь может закрыть и продолжить позже;
- concurrent stock change внутри ревизии: **HARD BLOCK только для затронутой строки / recount**, не для всего приложения.

## 4. Операции: перемещение, списание, корректировка

### Что уже хорошо в backend

- transfer/writeoff могут принять `observedPhysicalQuantity`;
- если по системе товара мало, но оператор реально видит достаточно, физический факт можно внести в той же операции;
- transfer не блокируется только потому, что после него существующим заказам станет не хватать товара: резервы сохраняются, система возвращает предупреждение;
- freshness/CAS и idempotency защищают от stale/double apply;
- полная активная ревизия блокирует физическое движение в той же точке, чтобы не смешивать две конкурирующие физические истины.

### P0: подтверждённый frontend/backend permission mismatch

`renderInventoryMovementPanel.tsx` блокирует общий submit условием:

`disabled={inventoryMovementBusy || !isAdmin || ...}`

Это делает кнопку недоступной обычному manager.

Но current Worker разрешает manager-safe routine операции:
- `manual_set` и `writeoff` без admin;
- известный `arrival` с готовыми `variantId` без admin;
- `/api/inventory/transfer` вообще не имеет admin gate.

Значит UI сейчас более строгий, чем бизнес-безопасность backend. Это прямое нарушение правила «не запрещать людям делать работу без веской причины».

Исправлять надо mode-aware, а не просто удалять безопасность: структурный/new-identity Arrival по-прежнему может требовать admin. **Arrival visual workspace не менять.**

### Класс

- известное перемещение/списание/корректировка: рабочая операция, не recovery task;
- если человек увидел расхождение во время действия: **INLINE OPTIONAL** внутри операции;
- нехватка резервам после transfer: **PARK**, предупреждение, не запрет;
- concurrent physical change: **HARD BLOCK только текущего submit** с просьбой обновить данные;
- активная полная ревизия точки: **HARD BLOCK физического движения**, с понятным объяснением.

### Nudge

Не спрашивать «сверьте склад» после каждого движения. Если операция уже получила physical observation — вторую проверку не предлагать. В дальнейшем давать микро-подсказку только при полезном контексте (например, уже обнаружено расхождение/сомнительный остаток), используя данные выбранной строки.

## 5. Выдача / отправка заказа

Backend уже проводит важное различие:

- физическая нехватка **не является** hard blocker для выдачи;
- реально присутствующее количество списывается без ухода physical ниже нуля;
- если пользователь добровольно передал observation, оно фиксируется перед выдачей;
- unresolved identity/variant остаётся all-or-nothing blocker, чтобы физическое списание не потерялось;
- historical handover ambiguity защищена CAS на конкретную физическую checkpoint.

### Класс

- ordinary physical shortage: **PARK / INLINE OPTIONAL**, но не запрет выдачи;
- unresolved variant, который невозможно физически списать корректно: **HARD BLOCK** конкретной выдачи;
- вопрос `к моменту проверки клиент уже получил товар?`: настоящий исторический факт — **INLINE REQUIRED at handover**, но не должен блокировать несвязанную работу;
- новый physical checkpoint, появившийся после открытия: **HARD BLOCK stale answer**, обновить только этот вопрос.

### UI cleanup later

Есть legacy-текст, отправляющий пользователя в `Склад → Товары → Требуют разбора`; после W2 это не должен быть навигационный ритуал. В идеале идентификация открывается как естественный detour прямо из выдачи либо остаётся в `Нужно уточнить`, если выдача сейчас не совершается.

## 6. Возврат

### Что уже хорошо

- возврат — critical/idempotent operation;
- для обычной складской/бутиковой позиции известный exact variant возвращается в остаток автоматически;
- товар, который по учёту вообще не выдавался, нельзя «вернуть в остаток» и удвоить — это обоснованный hard guard;
- Цех → Бутик запрещён как неверный физический маршрут;
- для Workshop пользователь явно решает, возвращается ли клиентская вещь в Склад.

### Класс

- ordinary known return inbound: **AUTO**;
- exact known Workshop return: целевая модель — как можно ближе к **AUTO**, если событие свежее и однозначное;
- неизвестная identity: **PARK**, физический факт «вещь уже здесь» не терять;
- попытка принять в остаток невыданную вещь: **HARD BLOCK**, потому что иначе будет двойной товар;
- Workshop → Boutique: **HARD BLOCK** данного маршрута, предложить безопасную альтернативу.

### Важный кандидат W3.4

`canAutoApplyFreshWorkshopInbound` требует trusted physical baseline. Поэтому exact-known Workshop inbound может остаться pending, если надёжной полной точки отсчёта нет. Для исторических pending events эта осторожность важна. Для **нового, только что созданного и явно подтверждённого физического возврата** возможно более естественное правило; менять его только после отдельного proof, чтобы не вернуть старые вещи второй раз.

### UI/copy

После успешного return frontend сейчас может сказать, что pending physical positions `ожидают подтверждения администратора`. Это слишком широкая формулировка: часть pending случаев — не структурное admin-решение. В W3 надо различать «неизвестно, что это за товар» и «товар известен, но безопасное применение пока отложено».

## 7. Обмен

Обмен — особый случай, потому что новая вещь по текущей семантике выдаётся физически в момент оформления.

### Что уже есть

- если новой позиции физически достаточно, обмен проходит;
- если по системе мало, форма предлагает уточнить фактическое количество;
- UI позволяет закрыть сам блок проверки кнопкой `Не уточнять`, но `saveExchange` снова остановит проведение, если physical всё ещё меньше требуемого;
- backend не принимает observation меньше количества, которое реально надо выдать;
- старая возвращённая вещь идёт через lifecycle; known ordinary inbound auto-applies, Workshop имеет freshness gate;
- stale old handover может быть безопасно reconciliation-ed перед приёмом возврата.

### Класс

- если `Оформить обмен` означает «физический обмен уже совершается сейчас», недостаток новой выдаваемой вещи — **HARD BLOCK с веской причиной**;
- добровольная physical correction при наличии вещи перед глазами — **INLINE OPTIONAL до submit**, но без достаточной физической вещи нельзя подтверждать совершённую выдачу;
- remote preparation обмена — текущая модель отдельного draft/pending не имеет. Не добавлять сложный workflow без реальной потребности; если пользователь позже скажет, что обмен часто оформляют заранее из дома, тогда рассмотреть `подготовить` vs `провести`.

UI должен явно объяснять, что hard block связан именно с фактической выдачей, а не с желанием базы получить красивое число.

## 8. Цех

`updateWorkshopTask` меняет статус/связь Workshop task и чинит workshop identity linked order item, но **сам по себе статус `ready/done` не является складской приёмкой**.

Не надо автоматически трактовать `Готово` как `+1 на Склад`: готовая вещь может идти клиенту, а не в складской остаток.

Workshop inbound для физического остатка появляется через возврат/обмен/lifecycle и должен оставаться отдельным физическим фактом.

### Класс

- task ready/done: обычный Workshop state, не складское движение;
- известный фактический возврат в Склад: **AUTO/INLINE** в конкретном return/intake flow;
- неизвестный вариант: **PARK** и точечная идентификация.

## 9. `Нужно уточнить`

Current Attention агрегирует пять классов: quantity, handover, intake, catalog identity, stocktake. Это полезный fallback, но не должно быть местом, куда пользователь обязан идти после каждой рабочей операции.

Цель W3.5 — после переноса/автовосстановления оставить здесь только то, что реально пережило естественный workflow.

Новый physical fact должен автоматически убрать устаревший вопрос, если он логически его разрешает. Карточку не надо «закрывать вручную» только ради уборки очереди.

## 10. Read-budget / скрытая загрузка Attention

### Найденный кандидат на ранний performance fix

`invalidateInventoryStockCaches()` сейчас не только сбрасывает локальный stock cache, но и делает:

`void loadWarehouseAttention(false, true)`

Из-за `force=true` это обходит summary TTL. Helper вызывается как минимум после создания/редактирования заказа, handover action, окончательной отправки и удаления. В нескольких shortage paths рядом также есть отдельный `loadWarehouseAttention()`.

После W2 global Attention badge уже не нужен, а исторически один Attention summary стоил около `2645 rows_read`. Поэтому forced summary после обычной операции вне Warehouse выглядит как лишняя скрытая цена и противоречит цели «Attention вторичен».

Перед изменением подтвердить source-call graph/regression locally, но **не делать Production profiling**: старых измерений достаточно.

Целевое правило: invalidation должна прежде всего помечать Attention cache устаревшим. Реальный read — когда пользователь открыл Warehouse/`Нужно уточнить` или когда конкретный текущий экран действительно использует эти данные. Никакой auto full Attention ради nudges.

## 11. Ещё два соседних UX-несоответствия

1. Когда короткая проверка заблокирована активной полной ревизией, Overview показывает кнопку `Открыть проверку` только admin, хотя manager имеет доступ к вкладке `Проверка`. Это не блокирует работу полностью (можно открыть через nav), но создаёт бессмысленную role-разницу.
2. Точечная история позиции из detail сейчас показана только admin, хотя общая Warehouse History manager-safe. Это не P0, но при последующем упрощении permissions надо решить, есть ли реальная причина скрывать read-only историю.

## Рекомендуемый порядок после W3.0

### W3.1A — reliability/read-budget preflight

Очень маленький патч перед nudges:

1. Исправить подтверждённый manager submit lock в `Операциях` mode-aware, не трогая visual Arrival.
2. Убрать лишний forced Attention summary из generic stock-cache invalidation; оставить cache invalidation и загрузку только по реальному demand.
3. Добавить focused regressions на manager movement modes, Arrival freeze и отсутствие unsolicited Attention read после ordinary order mutation.
4. Проверить adjacent: transfer/writeoff/manual_set/known-arrival, order create/edit/handover/shipping, W2.1 detail refresh ownership.

### W3.1B — первый добровольный micro-check

Начать с `Остатки → конкретный вариант` и существующего shortage/negative context. Никакой новой D1 таблицы и никакого глобального suggestion read.

- предложение только когда это действительно полезно;
- спокойный текст;
- один tap для открытия точечного ввода;
- можно закрыть без последствий;
- после успешного факта показать конкретную пользу (`Остаток обновлён`, а не баллы/очки);
- не спрашивать повторно в том же interaction после отказа.

После этого отдельно подключать natural contexts в Movement/Orders, а не размазывать новый компонент по всей системе сразу.

## Обязательные инварианты для реализации

- Arrival UI frozen.
- Branch2 untouched.
- No Production D1 forensic reads for W3.0/W3.1 unless a concrete question cannot be answered from source/tests and user approves larger scan.

- No blanket physical verification.
- No ordinary Warehouse shortage block for Workshop/order creation.
