# Архив завершённых Production workflow

8 ноября 2026 года из активной директории `.github/workflows/` перенесён набор из **21 исторического workflow** миграций, разовых SQL-коррекций и старых операций Production.

Основание: проверенный список устаревших сценариев из [PR #657](https://github.com/dymovicd123/Orders-app/pull/657). У этих workflow были триггеры на старые изменения файлов и устаревшие условия релиза, хотя соответствующие разовые операции закончены.

## Дополнение: завершённые релизные проверки Exchange и Finance

После первичной архивации 21 Production-операции в этот же каталог перенесены ещё 2 workflow:
- `main-p0-legacy-partial-exchange-20261027.yml`
- `main-p0-financial-atomic-20261027.yml`

Они были привязаны к замороженным коммитам октября, проверяли все изменения с тех SHA по старому allowlist и содержали ещё один прямой деплой Worker в Main. Их поведенческие проверки (реальный Worker HTTP/SQLite для обменов, возвраты, финансовые транзакции и исправление ошибочной отправки) сохранены в действующем `scripts/test-main-current-business-release-20261031.mjs`, вызываемом обязательным `npm run release:check`. Это **не** отключение бизнес-защиты ради зелёной CI: новые изменения доменов по-прежнему проходят тесты и современный `cloudflare-deploy-monitor`.

Также архивирован `test-main-return-active-reserve-p0.yml`: его исходный сценарий содержал неизменяемую ссылку на октябрьский SHA файла и прекращал выполнение при любом последующем рефакторинге. Действующая семантическая проверка `scripts/test-return-active-reserve-p0-20261021.mjs` уже включена в обязательный `release:check`, как и проверка создания/отмены возвратов и резервов. Тест исторического snapshot-replay остаётся в истории Git; не запускать его как проверку текущего приложения.

Автоматический архивный guard теперь защищает **24 исторических workflow**. Исходные YAML сохранены байт-в-байт.

## Что изменилось

- Архивные YAML сохранены **байт-в-байт** здесь, под исходными именами.
- GitHub Actions больше не регистрирует эти файлы как активные workflow, следовательно случайное изменение миграции или архивного сценария не запустит старую операцию над Production.
- История исполнения и прежние версии доступны в GitHub через историю коммитов.
- Современные `Quality check`, `cloudflare-deploy-monitor`, текущие QA и release workflows остаются в `.github/workflows/`.
- Отсутствие архивных файлов в активной директории защищает `scripts/test-ci-historical-workflow-archive-20261108.mjs`, выполняемый в обязательном `release:check`.

## Если когда-либо нужно повторить миграцию

Не копируйте архивный workflow обратно и не запускайте старый SQL без нового review. Следует создать отдельный, датированный план изменений с проверкой уже применённой схемы, точной базы данных и dry-run на Branch2. Для Main нужны явное согласование, idempotency/preflight и отдельная проверка после исполнения.

Сценарии `one-off` не заменяют современный путь выпуска Cloudflare Worker. Это исторические источники, а не активные инструменты.

## Что ещё требует ревизии

Остальные workflow и `scripts/test-*` необходимо классифицировать по текущей ответственности и актуальности. Отсутствие прямой ссылки в CI ещё не означает, что тест можно удалить: он может использоваться вручную или быть частью другой матрицы.
